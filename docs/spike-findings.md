# Round-trip spike: findings

**Date:** 2026-10-20
**Question:** is "code on disk is the only source of truth, and the canvas patches byte ranges"
sound enough to build twowayflow on?
**Answer:** yes, with three caveats that are written down below rather than discovered later.

This document is deliberately blunt about what was and was not verified. A spike that only
reports good news is not a spike.

---

## 1. What was built

| Piece | State |
|---|---|
| pnpm monorepo, TypeScript strict, Biome, Vitest | done |
| `*.flow.ts` eDSL, designed before implementation ([docs/dsl.md](dsl.md)) | done |
| Two worked examples in `examples/` | done |
| tree-sitter parse → graph with a byte span on every node, edge and endpoint | done |
| Patch API: add/delete node, add/delete edge, rename, move — each returning ranged text edits | done |
| VS Code extension: `@xyflow/react` canvas, continuous two-way sync, selection sync both ways | done |
| Property-based round-trip suite (fast-check) | done — **this is the deliverable** |
| Real extension-host integration test | done, separate from `pnpm test` (needs a display) |

`pnpm install && pnpm test` passes from a clean clone: 100 tests across 5 files, no display, no
network, no build step needed first. Verified by exporting the tracked files to an empty
directory and running it there.

## 2. What held up

### Byte-range patching is sound. This is the headline.

Every operation is a small, local, unambiguous edit, and the property suite says so across a
generated corpus. The results below are from `TWF_FC_RUNS=12000`, i.e. 12,000 generated cases for
each property in the table:

| Property | Result |
|---|---|
| `reassembleFromLinks(parse(src)) === src` — the recorded spans tile the file exactly, in order, with no overlap | green |
| Every inner span (`idSpan`, `positionSpan`, `optionsSpan`, edge endpoints) holds exactly the text it claims and nests inside its parent | green |
| `parse` recovers the generated graph regardless of formatting, trivia, option-key order or trailing commas | green |
| The canonical printer round-trips and is idempotent | green |
| `parse(applyEdits(src, patch(ops)))` ≡ `applyOps(parse(src), ops)` — single op, op sequences re-parsed between each step, and independent batches | green |
| Every comment in the input is present, unchanged, in the output of any patch or sequence of patches | green |
| Untouched nodes keep their source text byte-for-byte after any operation | green |
| Links the parser refuses come out of a patch byte-for-byte unchanged | green |
| A patch touches a bounded number of bytes, never the file | green |
| Deleting an edge leaves every other edge's identity alone — directly, and via a node deletion that takes several edges with it | green (see §3.2) |

Edges are generated both with and without a declared `id` (§3.2), in all three argument-spacing
styles and with the option keys in either order, so the identity rules above are exercised rather
than assumed.

The corpus is generated by rendering random graphs through randomised formatting: tabs,
over-indentation, blank lines, tight `{kind:"x",at:[0,0]}`, multi-line option objects, trailing
commas, reordered keys, extra opaque keys, and ten kinds of inter-link trivia including line
comments, block comments and inline comments. Two unparsable links are injected into a fraction
of generated files.

### Span provenance survives editing

The sequence property is the one that matters for the editor: it applies up to six operations one
at a time, **re-parsing between each**, and asserts span integrity, lossless reassembly and
model agreement at *every* step. That is the real usage pattern — the editor re-parses after each
keystroke — and a span that is briefly wrong is a bug the user sees. It holds.

Node identity is a declared string id, so "edit the code and the node moves rather than being
destroyed and recreated" is true by construction rather than by heuristic matching. The
integration test confirms it in the real host: changing `at: [240, 0]` in the text moves the node
and leaves its neighbours identical.

### tree-sitter was the right call, and the WASM route works in TypeScript

`web-tree-sitter` 0.27 plus the prebuilt TypeScript grammar from `@vscode/tree-sitter-wasm` 0.3
parses and gives exact offsets, with no native compilation anywhere. Error tolerance is real: the
half-typed fixture (`.node("inProgress", { kind: "trans`) still yields the three valid nodes
beside the syntax error, which is what lets the canvas stay open while someone types.

One wrinkle worth recording: `@vscode/tree-sitter-wasm` ships its *own* `tree-sitter.wasm`
runtime built against VS Code's emscripten glue, and loading it with `web-tree-sitter` 0.27 fails
with an opaque `LinkError`. Take only the grammar from that package and let web-tree-sitter load
its own runtime.

### The chained-builder DSL patches as advertised

All four claims in [docs/dsl.md](dsl.md) §2 are now tested:

- insert a node / add an edge → a single zero-width insertion, no bytes deleted;
- rename → N replacements of the text *between* the quotes, three for a node with two edges;
- move → one replacement of the `[x, y]` array literal, with the `run:` closure sitting beside it
  untouched;
- delete → one contiguous deletion per element.

### A canvas with no model of its own is simpler, not harder

The webview keeps no local graph state. A drag sends `moveNode` and renders nothing; the
extension patches the file, the file change re-parses, and the new graph arrives. The canvas
always displays what the file says. This removes the entire class of bug the architecture exists
to avoid, and it removed code rather than adding it.

## 3. What did not hold up, or needs a decision

### 3.1 Batched operations are not well defined, and the fix is "don't batch"

The property suite found three distinct ways a batch of two operations can diverge from applying
the same two operations to the model in sequence. All three are inherent to computing edits
against one snapshot of the source:

1. `[addEdge("a","a"), renameNode("a","aa")]` — the model renames the new edge's endpoints; the
   patcher computed the rename's spans before that edge's text existed.
2. `[renameNode("a","aa"), moveNode("a", …)]` — the patcher applies both, because both resolved
   against the original spans; the model looks the node up by id and the second op silently
   misses.
3. `[deleteEdge("a->b"), deleteEdge("a->b#1")]` — see 3.2. **Fixed**, but not by declared edge
   ids. Declaring ids avoids it only when ids are declared; the divergence remained for
   *undeclared* parallel edges, which is still the default. What fixed it was making the model
   resolve edge identity **once per batch**, the way the patcher already resolved spans. See
   3.2.

None of these is a bug in the patcher or the model. The batch is simply ambiguous. **The
resolution adopted:** operations in one batch must be independent, `patch()` throws on the
overlapping-edit cases it can detect, and the extension sends **one operation per
`WorkspaceEdit`**. That is also better UX — one undo step per gesture — so the constraint costs
nothing today. It would cost something if multi-select drag is ever wanted, which would need
either op rebasing or a single compound op.

The batch property test encodes the independence rule explicitly, so this constraint is now
enforced rather than remembered. Two of the three cases above remain; the third was a
consequence of §3.2 and went away with it.

### 3.2 Edge identity was positional. It is declared now.

**Fixed.** This section used to recommend the change; it now describes what the code does.

The problem, as the spike left it: node identity was a declared string and edge identity was not.
An edge was keyed `from->to`, with `#1`, `#2` suffixes for parallel edges between the same pair,
so deleting one parallel edge renumbered its siblings and an id captured a moment earlier could
silently come to mean a different edge. The property suite could not even generate the case — the
batch property carried an explicit rule rejecting any batch with more than one edge-deleting op
when the graph had parallel edges, which was a workaround for the design, not a constraint on it.

What `.edge()` does now ([docs/dsl.md](dsl.md) §1):

```ts
  .edge("fanIn", "merge", { label: "default route" })
  .edge("fanIn", "merge", { id: "fast-path", label: "cached" })
  .edge("fanIn", "merge", { id: "slow-path", label: "recomputed" })
```

- A declared `id` is that edge's identity outright. It survives its siblings being deleted and
  survives both its endpoints being renamed.
- Without one, identity is still `from->to` plus a `#n` suffix — so every file written before
  this change parses to exactly the same graph it did before, which is the point. The suffix now
  counts only the **undeclared** edges of a pair, so declaring an id on one parallel edge does not
  renumber the others.
- The canvas declares an id on every parallel edge it creates (`suggestEdgeId`), choosing the
  string the positional scheme would have produced anyway. Nothing the user sees changes shape;
  the identity becomes something written down rather than counted.
- Declaring the same id twice is a `duplicate-edge-id` diagnostic, and the patcher refuses to act
  on an ambiguous id rather than guessing.

**A correction to the above, found by reviewing it.** Removing the parallel-edge rule from
`batchIsSafe` was premature: the rule excluded a case that declared ids only *partly* fix.

An edge without a declared id is still positional, so deleting one such edge still renumbers its
undeclared siblings — and `applyOpsToSpec` recomputed ids after every op while `patch()` resolved
every op against one snapshot. The two therefore still disagreed, for exactly the batch the rule
used to exclude:

```ts
  .edge("a", "b")          // ids: "a->b"
  .edge("a", "b");         //      "a->b#1"

  // batch: [deleteEdge("a->b"), deleteEdge("a->b#1")]
  //   patched text -> 0 edges   (both links resolved against the original snapshot)
  //   model        -> 1 edge    ("a->b#1" no longer existed after the first delete)
```

Eight lines reproduce it, yet a 12,000-run pass was green: the generator reaches parallel edges
and reaches two-delete batches, but rarely both at once on an *undeclared* pair. So the suite had
stopped excluding the case without starting to cover it, which is worse than the rule it replaced.

**The fix.** `applyOpsToSpec` now resolves edge identity once, from the spec the ops were computed
against, and carries it; `deleteEdge` matches that carried id instead of recomputing. The model
and the patcher now share the snapshot semantics that `patch()` always had, so the batch is well
defined for declared and undeclared edges alike, and nothing has to be forbidden.

Two things guard it, and both were checked by deleting the fix and watching them fail:

- deterministic cases in `packages/core/test/patch.test.ts` covering two parallel edges deleted
  together, one of two, declared ids, and a `deleteNode` cascading over both;
- a dedicated property that *constructs* the shape — n edges between one pair, each independently
  declared or not, an arbitrary subset deleted in one batch — rather than waiting for the general
  generator to stumble into it.

What this bought in the test suite:

- The parallel-edge rule is **gone** from `batchIsSafe`, and two edge deletions in one batch are
  now a case the suite exercises rather than skips (~470 such batches per 12,000-run property).
- A new property says what declared ids are for: *deleting an edge leaves every other edge's
  identity alone*, asserted both for `deleteEdge` and for a `deleteNode` that takes several edges
  down with it.

**What is still positional, stated plainly.** An edge's identity depends on another edge still
existing in exactly one shape: a pair with two or more *undeclared* parallel edges. Delete the
first and the rest renumber, exactly as before. The canvas never writes that shape, so it only
arises in a hand-written file, and naming the edges fixes it. The property suite is explicit
about the boundary rather than quiet about it: `arbGraph` generates that shape and every
single-operation property runs against it, while the two properties that need an id to mean the
same thing before and after an edit — identity stability, and batches with more than one
edge-deleting op — run against `arbStableGraph`, which maintains the invariant the canvas
maintains. Flipping that generator back makes both properties fail within a few hundred cases,
which is the evidence that the rule was removed for a reason rather than because it had stopped
firing.

### 3.3 Comments are preserved absolutely; comment *attachment* degrades

The suite guarantees that no patch loses a comment — the multiset of comment tokens is identical
before and after, across every generated case. That is the invariant that matters and it is
unconditional.

Attachment is weaker. A link's deletion range covers the link plus only the *whitespace* before
it, so a comment between two links is outside every deletion range. Deleting the node it
described therefore leaves the comment pointing at nothing:

```ts
  .node("ingest", { kind: "source", at: [0, 0] })
  /* block comment between links */ // trailing note on the clean node
  .node("store", { kind: "sink", at: [480, 0] })
  // the two edges below are load bearing
  ;
```

That is the real output of deleting `clean` from
`packages/core/test/fixtures/comments-between-nodes.flow.ts`. It compiles, every comment is
there, and two of them are now in the wrong place.

This was a deliberate trade: eating a comment is unforgivable and orphaning one is merely untidy.
A v2 could attach leading comments to the link that follows them and delete them together, with a
prompt. It should not do so silently.

Related: the same fixture found a genuine bug during the spike. Two adjacent deletions each
looked harmless alone and together moved the trailing `;` onto a `//` line, commenting out live
code. The stranding check is now resolved across the whole batch, back-to-front, with each
deletion seeing what the ones after it decided to leave behind.

### 3.4 Positions in source code are a real cost, accepted

`at: [x, y]` lives in the file. Tidying a canvas therefore produces a diff. The alternative —
a sidecar layout file — is the first step back towards the `.twf` model the architecture exists to
reject, so it was not taken. Keeping `at` inline means a node and its position move, merge,
revert and `git blame` as one thing. Stated here so nobody relitigates it by accident.

### 3.5 A few sharp edges in formatting output

Patching into tightly-formatted source produces valid but slightly ugly output —
`{ at: [1, 2],kind:"map"}` when inserting into `{kind:"map"}`. The patcher inserts a space when
the next character is not whitespace, which covers the common case, but it does not and should not
reformat its surroundings. Deterministic formatting on write (the plan from the assessment) would
tidy this, and is not needed for correctness.

That last row is the honest limit of this spike. If a reviewer wants the gesture itself
confirmed, press <kbd>F5</kbd> and drag a node; everything it depends on is covered by tests.

### 3.6 Two small things the integration test caught

Worth recording because both are the kind of thing that only shows up in a real host:

- The extension originally declared `activationEvents: ["onLanguage:typescript"]`, which loads it
  for *every* TypeScript file. Since VS Code 1.74 a `contributes.commands` entry gives implicit
  `onCommand` activation, so the list is now empty and the extension loads when the canvas is
  actually asked for. The editor-title button still appears, because menu contributions are read
  from the manifest without activating anything.
- `@vscode/tree-sitter-wasm` and `web-tree-sitter` both ship a `tree-sitter` runtime WASM and they
  are not interchangeable (§2). The build copies the correct pair into `dist/`, the extension
  addresses them by absolute path so a packaged `.vsix` does not need node_modules, and it falls
  back to node_modules resolution when `dist/` has not been built — which is what lets
  `pnpm install && pnpm test` work on a clean clone with no build step.

## 5. Verdict

**Build on it.** The approach is sound, the two make-or-break risks from the tech-stack
assessment are both addressed and both now have tests that fail if they regress, and the failures
the suite found were real and fixable rather than structural.

Recommended order of work next:

1. ~~**Declared edge ids** (§3.2)~~ — **done**, see §3.2. It was the only DSL change this spike
   recommended, and doing it first was right: it is a change to the file format, and the file
   format is the thing that is expensive to change later.
2. **Deterministic formatting on write** (§3.5), which also makes the canonical printer's output
   and hand-written files converge.
3. **The Rust core**, once the TypeScript implementation's behaviour is pinned by the property
   suite. Port it against the same properties — they are the specification, and they are
   language-agnostic.
4. **Comment attachment on delete** (§3.3), with a prompt rather than silently.
5. Leave multi-select drag until there is a reason to want it, and when there is, decide between
   op rebasing and compound ops rather than loosening the batch rule.

The property suite is the product. If it is green, the IDE works. Keep it that way.
